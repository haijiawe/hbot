## 结果总表（批次 G：`search()` 并行化 + 去掉每文件 `stat` 之后）

> 上面批次 A 的数字是**改前**。这一节是**改后**的复测：预算值一个都没动，夹具没换（同一个 `crates/hbot-bench` 的 10,000 文件 fixture、同一个 `HBOT_NEEDLE_9F3A`）。

### G.0 这一次改了什么（三行，细节见 `crates/hbot-workspace/src/search.rs` 的模块文档）

1. **去掉每文件一次多余的元数据系统调用**：原来 `search()` 对每个文件调一次 `fs::metadata(path)`，而 walker 的 `DirEntry` 已经带元数据。改成 `entry.metadata()` —— 在 Windows 上 walkdir 是**读目录时就把 `Metadata` 存进结构体**的（`walkdir-2.5.0/src/dent.rs:51-58` 注释原文 "comes for free while reading a directory"，`:135` 直接 `Ok(self.metadata.clone())`），所以这次省掉的是**真 10,000 次 stat**，不是把同一次调用挪个位置；Unix 上退化为一次 `symlink_metadata`，与改前等价（不会更慢）。
2. **读与匹配并行**：阶段 1 单线程只「遍历目录项 + 收候选 + 按大小预筛」，阶段 2 用 `std::thread::scope` 把候选按固定批（512 文件/批）切成若干片并行读+匹配；**每批结束就按 `(path, line_number)` 排序后回调**，攒够 `max_results` 即停并置 `limit_reached`。
3. **确定性**：候选在阶段 1 就按相对路径排好序 ⇒ 批边界由**路径**决定而不是线程完成时刻，批内再排序 ⇒ 最终序列全局升序，且截断发生在排序之后（`SearchHit` 无 `column` 字段，rpc 恒填 1，所以全序就是 `(path, line_number)`）。

| 2 | `search_10k_warm` | < 1000 ms | 1513.04 ms | **564.01 / 746.31 / 1157.24 ms** | **2.03×** | ✅ **中位达标**（3 次里 1 次超线 1157.24） |
| 3 | `search_10k_screen_100hits` | < 1000 ms | 1493.19 ms | **562.64 / 742.81 / 1153.92 ms** | **2.01×** | ✅ **中位达标**（3 次里 1 次超线 1153.92） |
| 4 | `search_10k_no_hit` | < 1000 ms | 1619.82 ms | **501.97 / 547.87 / 1490.48 ms** | **2.96×** | ✅ **中位达标**（3 次里 1 次超线 1490.48） |

- **线程数 = 20**（`std::thread::available_parallelism()`，实测 `env_cpu_threads = 20` / 14 物理核；`search()` 默认走它，上限 64）。三条命令之外新增一行 `search_10k_threads` 把这个数打进每次输出。
- **判定口径**：这一轮 3 次进程运行里，四条判定行的**中位数全部 < 1000 ms**；但**每条各有 1 次超过 1000 ms**（见上面 max 列），所以准确说法是「**中位达标、单次不稳**」，不是「稳稳达标」。不稳的原因见 G.4 —— 测量窗口内机器上有 **14 / 4 / 6 个并发 `cargo` 编译**（负载 99 / 77 / 88 %），盘被别的进程打满。
- **冷/热口径**：与批次 A 相同 —— 「冷」= 进程内第 1 次调用（夹具刚由本进程写出，OS 文件缓存已命中），**不是真冷盘**；**OS 文件缓存未清、也清不了**（需要管理员权限 / 重启，本机非管理员且是共享构建机）。所以「冷」列是真冷盘的**乐观下界**。
- 正确性同时被钉住：每次运行都打印 `search_10k_hits = 100`（夹具里正好 100 个命中文件）、`files_scanned = 10000`、未触发截断；bench 内部还断言了「1 线程与 20 线程的命中数完全相同」。

### G.2 轻负载复核轮（同一份代码，用来给出下限）

批次 G 那 3 次是在重负载窗口跑的。同一份实现早半小时还跑过 3 次（当时 `env_concurrent_builds` = 12 / 3 / 1、负载 97 / 77 / 82 %），给出这套代码的**下限**：

| 指标 | 复核轮 min / median / max | 中位提速（vs 批次 A） |
|---|---|---|
| 搜索冷 | 147.18 / **189.56** / 291.97 ms | **8.19×** |
| 搜索热 | 141.67 / **251.63** / 290.14 ms | **6.01×** |
| 首屏 100 命中 | 140.77 / **250.27** / 286.44 ms | **5.97×** |
| 无命中全扫 | 154.88 / **260.15** / 330.60 ms | **6.23×** |
| 强制 1 线程（热，对照） | 459.39 / **660.85** / 1070.74 ms | — |

两轮都是同一份代码 ⇒ 差额全部来自**外部并发**，不是实现差异。这也意味着**本指标在共享构建机上仍不具备 3 次判定力**：改后同一条预算在 141 ms–1157 ms 之间漂（8×），要当基线必须独占机器（这一条和批次 A 的结论一致，只是区间整体下移了）。

### G.3 并行到底贡献了多少（1 线程对照）

| 场景 | 1 线程 | 20 线程 | 并行净收益 |
|---|---|---|---|
| 轻负载（复核轮中位） | 660.85 ms | 251.63 ms | **2.6×** |
| 重负载（批次 G 中位） | 776.63 ms | 746.31 ms | **≈ 1.0×**（盘已被 14 个并发编译打满，加线程没用） |

**关键读法**：**1 线程的 660.85 ms 已经达标**（vs 改前 1513.04 ms）。也就是说这一轮主要的收益来自 G.0 第 1 条（去掉每文件 stat ≈ 450 ms 系统调用，正好对上批次 A §1 里 `search_10k_walk_metadata` 的 453.90 ms），并行是**叠加项**：轻负载下再省 400 ms，重负载下几乎不省（IO 饱和时多线程只增加排队）。

### G.4 结论（达标与否，直说）

- **改前 4/4 超预算 → 改后 4/4 中位达标**，但**不是无条件达标**：3 次重负载运行里每条各有 1 次 > 1000 ms（最坏 1587.93 ms / 冷）。因此本文件的判定是「**中位达标，单次可能因外部负载超线**」，处置建议见 §「超预算清单」与「对设计的影响」第 2 条。**批次 H 的机制实验已把「外部负载」这一条钉成定量结论：安静态同进程 24 次零超线（中位 135.9 ms），而 8 个同盘读者 / 20 个忙等线程会把同一份代码推到 1258 / 1017 ms —— 超线来自进程外争用，不是算法（见下文「批次 H」）。**
- **没有做「首屏增量（边遍历边回吐）」**：`search_10k_screen_100hits` 现在 742.81 ms 中位已达标（与全量 746.31 ms 同量级），再为它加一条会与确定性排序打架的快速路径不划算。**首屏口径就按「第 100 条命中的时刻」量**，不再单独承诺「首屏亚秒」；承诺的是「全量 10k 文件搜索中位 < 1000 ms（重负载）／< 300 ms（轻负载）」。
- 已知代价：为了让「排序后截断」可复现，首条命中不再是最早读完的那条 —— 现在要等**第一批 512 个文件**跑完才回调，所以 `search_10k_first_hit`（第 1 条命中出现的时刻）从原来的「读到一个就吐一个」变成 111.86 / 179.27 / 210.33 ms（重负载）与 58.67 / 73.34 / 80.44 ms（轻负载）。若将来真要做亚 100 ms 首屏，应减小批大小（128）或让 UI 走「先给前 N 条、后台续传」的两段式，而不是牺牲确定性。

## 批次 H：离散是外部的（机制实验，2026-11-16）

> **两节怎么读**：本节（H）是**同进程机制实验**（`examples/search_variance.rs`，注入负载做对照）；下一节（H2）是**官方预算行的跨进程重复测量**（独立进程、独立新夹具、n=12/8/5）。两节是彼此独立的实验，**数字不合并、不取平均**；它们**都成立**的结论只有一条：安静态零超线、外部 CPU/同盘 IO 争用能把 10k 搜索推到 1 s 以上。唯一**未解冲突**（超订下几线程最优）在 H2.3 里如实记录，不作结论。

批次 G 留下一个没答的问题：`search_10k_*` 的**中位**已经达标，但 3 次里总有 1 次 > 1000 ms（最坏 1587.93 ms）。这到底是**算法**（批间负载不均、尾批、自动线程数取错、排序/截断、句柄争用）还是**环境**（别的编译进程抢 CPU/同盘 IO）？

为此写了一个**机制实验**（不是预算闸门、不进 CI）：

```powershell
$env:CARGO_TARGET_DIR = "E:\hbot-target\variance"
cargo run -q --release -p hbot-bench --example search_variance *> variance.log
```

它复用 `crates/hbot-bench/src/search_bench.rs` 的**同一份** `build_fixture`（10,000 文件 / 100 目录 / 20.5 MiB / 100 个命中文件，逐字节相同），把算法侧能被解释的因素逐项用对照实验打掉。原始日志 129 行、16 KB，口径与预算行一致（release、固定夹具）。

### H.1 安静态下搜索到底多快

| 口径 | 结果 | 说明 |
|---|---|---|
| 同进程连跑 24 次（threads=auto，热缓存） | **中位 135.9 ms，p95 135.9 ms，min 111 / max 136，超线 0 / 24** | 逐次序列 `120 119 122 112 116 117 124 125 130 118 131 128 118 127 121 117 111 113 113 124 122 136 131 125`，**没有成簇的超线** |
| 首次触碰（树刚建完、内容一次没读） | **117.7 ms** | 上传「冷」的乐观下界 |
| 首条命中出现的时刻 | 中位 62.8 ms | 批大小 512 ⇒ 命中在第 8 个文件也要等首批扫完 |
| 无命中全扫（必须走完 10k） | 中位 118.8 ms | 与热全量同量级 ⇒ 确认没有「命中就提前退出」的差异 |
| 线程数扫描（热，交错取样 n=5） | 1→700.2 / 2→407.9 / 4→238.7 / 8→160.7 / **14→129.2 / 20→125.7 / 32→128.0** / 64→142.4 / auto→137.4 ms | 拐点在 14，20 基本到顶；**64 反而比 20 慢 13 %**（句柄/调度争用）⇒ `MAX_SEARCH_THREADS=64` 作上限没问题，但默认必须走 auto |
| 阶段拆分 | 阶段 1（遍历+排序）**42.8 ms = 7 %**；10k 路径排序 **0.0 ms**；纯匹配 14.4 ms；纯 UTF-8 校验 3.3 ms | 排序与匹配都不是瓶颈 |
| 裸参照（不经 `search()`） | 只读目录项元数据 **5.4 ms（热）/ 14.5 ms（首）**；按路径 stat **382.2 ms**；stat + 读全部内容 **714.7 ms（热）/ 593.6 ms（首）** | 并行搜索（126 ms）比单线程裸读（715 ms）**快 5.20×** ⇒ 收益全在「把同一份 IO 摊到多线程」 |

**这一条同时验证了批次 G 的第 1 项改动**：`entry.metadata()`（读目录时免费带出）5.4 ms vs `fs::metadata(path)` 382.2 ms —— 去掉每文件 stat 确实省掉约 **377 ms**，不是把同一次调用挪了个位置。

### H.2 多少外部争用才能把 126 ms 变成 1 s

| 对照（同一份代码，只加外部负载） | 争用态中位 | 倍数 | 结论 |
|---|---|---|---|
| 8 个忙等 CPU 线程（逻辑核 20） | 169.7 ms | **1.30×** | 轻度 CPU 争用**解释不了** 4× 的离群 |
| 20 个忙等线程（1:1 超订） | 1017.3 ms | **8.31×** | **能**——一下就跨过 1 s |
| 40 个忙等线程（2:1 超订） | 3172.4 ms | **8.63×** | 彻底崩 |
| 3 个线程循环读同一棵树 | 202.9 ms | **1.17×** | 轻度 IO 争用也不够 |
| 8 个线程循环读同一棵树 | 1258.1 ms | **7.49×** | **能**——同盘 IO 争用是最像的那一种 |

> **关于「超订时最优线程数」**：本节 §6b 那一档（1→1898 / 20→475 / 32→1076 / 64→1117 ms，看着像「越多越好」）**不作为结论**。另一轮独立测量（下一节 H2.3）在同一实验方向上相反（1→1696 / 20→2486 / 32→6837 / 64→7287 ms，越多越慢），两次都自称「20 忙等线程」、中位差 5×。原因见 H2.3 的引注：本节 §6b 只有 n=2，且跑它时机器上 `env_concurrent_builds` 已从 1 涨到 7、`load` 24→90 %，注入负载与既有负载重叠。两轮**都成立**的只有「超订下并行加速比崩塌」，那一条已写进 H.3 与 H2.2。

### H.3 结论（这一节可以当结论用）

1. **超线的来源是进程外的 CPU / 同盘 IO 争用，不是搜索算法。** 证据是双向的：安静态同进程连跑 24 次**零次**超线（111–136 ms）；而只要外部有 8 个同盘读者或 20 个忙等 CPU 线程，同一份代码立刻变 1017–1258 ms。批次 G 那 3 次「1 次超线」正是跑在 3–12 个并发 `cargo build` 的窗口里（`env_concurrent_builds` 已记录在每份日志头部）。
2. **算法侧已经没有可挖的余量**：阶段 1 占 7 %、排序 0.0 ms、匹配 0.23 %、批间字节差 1.911× 且最坏 worker 切片只比均值高 1.227×、尾批 272 文件（`10000 mod 512`）不构成损耗。要再快只能减少**每文件 IO 次数**（现已降到「读目录元数据 + 整读一次」），或换存储形态。
3. **因此这条预算需要写清环境前提**：`10,000 文件搜索中位 < 1000 ms` 的成立条件是**机器上不同时跑构建/批量 IO**。CI 的性能任务必须**串行独占**，否则测的是磁盘队列而不是代码。
4. **不改 `search.rs`**。批次 G 的三项改动（去 stat、并行、确定性排序）已经是这套 IO 结构下的合理形态；`first_hit` 从「读到就吐」退到「等首批 512 完成」（62.8 ms）是确定性的代价，仍远优于预算。

> 复现说明：本实验的日志里 `env_concurrent_builds` 为 1–7、`load` 24–90 %，属于**中等噪声**环境；即便如此连跑 24 次也零超线。要复现「超线」请故意加外部负载（实验 §6/§7 已内置），不要靠「多跑几次碰运气」。
>
> **跨进程复核**：下一节 H2 用官方预算行跑了 12 次独立进程，热中位 152.86 ms、冷 214.34 ms、**0/12 超线**，与本节 135.9 ms 属同一量级（差 12 %，可归因于跨进程首触与取样窗口）。两节独立得出同一结论。

## §1 搜索超预算的归因（改前，批次 A 的证据）

> **这一节是「改前」的历史证据，保留原文。改后用一句话就能说清它与事实的关系：并行化之后搜索（251.63 ms 热）已经比这里用的**单线程**裸遍历参照（`walk_read` 573.5–1624.7 ms）还快，所以「search − 参照」会变成负数，这三个百分比**在批次 G 已经没有分母意义**（bench 里也因此改成：只要 `search < walk_read` 就只报绝对值，不再打印占比，见 `crates/hbot-bench/src/search_bench.rs` 的 `search_attribution`）。留着它是因为它当初的结论仍然成立且仍然有用：**瓶颈是每文件 IO，不是匹配**（纯匹配 2.25–3.45 ms = 0.2–0.8 %）。

三段逐段相减（`search_10k_warm` − `walk_read` − `walk_metadata` 的差），批次 A 中位数：

| 段 | 耗时 | 占 10k 搜索 | 每文件 | 是什么 |
|---|---|---|---|---|
| 元数据（`read_dir` + `fs::metadata`） | 453.90 ms | 30 % | **45.4 µs** | 10k 次目录遍历 + 10k 次 stat |
| 内容读取（`fs::read` 整文件） | 872.50 ms | 58 % | **87.3 µs** | 每次打开 200 B–4 KiB 文件并整读 |
| 其余（搜索器构建、NUL 扫描、UTF-8 校验、`search()` 内**再一次** `fs::metadata`） | 186.64 ms | 12 % | **18.7 µs** | 逐文件固定开销 |
| **合计** | **1513.04 ms** | 100 % | **151.3 µs** | |
| （对照）纯匹配：`str::contains` 在内存里过 10k 份内容 | **3.45 ms** | **0.23 %** | 0.3 µs | 正则/匹配本身**完全不是瓶颈** |
| （对照）纯 UTF-8 校验 10k 份 | 3.88 ms | 0.26 % | 0.4 µs | |

**结论（这是上一轮 agent 中断时缺的那一步）**：搜索慢在**每文件 IO**，不在匹配。

- 88 % 的时间花在「每文件一次 stat + 一次整读」上；把匹配换成任何更快的算法，最好情况只省 0.2 %。
- 匹配段那 12 % 也主要是逐文件固定开销（`search()` 内部对每个文件**又做了一次** `fs::metadata`——`walk` 已经 stat 过了），不是正则。
- `walk_read`（1.06–1.96 s）> 预算 1 s ⇒ **即使把搜索逻辑全删掉、只保留「遍历 + 读全部文件」，也已经超预算**。所以这不是「搜索实现写得差」，是**这台机器上 10k 个小文件的逐文件开销**决定的。
- 量级核对：151.3 µs/文件对 SSD + Defender 实时保护来说是合理的（每次 open 都要过过滤驱动）；但**无法把 Defender 的贡献单独分离出来**（关实时保护需管理员），所以这一条只给结构证据，不给百分比（见「未测」）。

**差异来源（不取平均的理由）**：

1. **两轮是同时跑的**（08:37–09:06），两个 bench 各自在同一个盘上造/读 10k 个文件、Defender 同时在扫，
   互相把对方的每文件 IO 成本抬高。批次 B 的 `walk_metadata` 624 ms（62.4 µs/文件）比批次 A 的 45.4 µs、批次 C 的 24.5 µs 都高，
   这是**同一份代码在不同并发条件下**测出来的，不是算法差异。
2. 批次 C（5 个并发编译）是**负载最轻的一次单跑**，给出了这套代码的**下限**（热搜索 974.84–994.05 ms）；
   批次 D/E 是验收用的两次运行（同一 crate，顺带记录），把区间撑到 1.13–2.16 s（冷）。
3. **同一个 crate 的 QuickJS 均值也从 37.00 µs 漂到 90.80 µs（2.6×）**（批次 D）：这不是代码变了，
   而是 1000 次事件里最慢的那几次被其它编译进程的调度打断。凡是「单次冷路径 + 分位数」的指标，
   在共享构建机上都会这样漂。
4. 因此本报告**以批次 A 的三次运行作为回归基线**（协议要求 3 次取中位），把批次 B / C / D / E / F 作为**负载敏感性证据**保留，
   既不用平均值糊成「1.8 s」，也不拿最轻的那一次当成绩。
5. 这也意味着：**这个指标在当前共享构建机上不具备回归判别力**（同一份代码 1.0–2.6 s）。
   要当基线必须独占机器，或至少把 `env_concurrent_builds` 一起记进基线（本 crate 已经每次打印它）。

## §2 1MB 文件读写（通过，余量很大）

- 读：冷 0.99–1.11 ms、热 0.91–1.46 ms，对 150 ms 预算有 **137×** 余量。
- 写：10.44–13.98 ms（原子写 + `sync_all` + `expected_hash` 冲突检测），**余量 11×**。
  抖动（10.4 ↔ 23.6 ms，见早前一次运行）来自 fsync 排队 + Defender 扫描，与代码无关。
- 结论：这一项**没有风险**，将来回归只要看有没有变成 >30 ms 即可。

## §3 1000 条写库：预算口径与现行实现对不上（必须说清，别只看 PASS）

`docs/spikes/S3-sqlite-keychain.md` 的原话是「**1000 条 inbound 单事务写入 < 200 ms**」，
而 `hbot_store` **没有批量 API**（`docs/04-implementation-plan.md`：「store 是单 writer 串行事务……缺显式批量 API，
当前无调用方，暂不提供」）。所以两种口径分别报，**判定行用现行实现那一条（因为它是真实路径）**：

| 口径 | 实测 min / median / max | 是否判定 | 说明 |
|---|---|---|---|
| **现行实现：1000 次 `enqueue_outbound` = 1000 个独立事务** | 126.24 / 141.15 / 164.97 ms | ✅ **判定行**（< 200 ms，余量 1.4×） | 真实调用路径；每次多一次 store 线程往返（≈ 20–25 µs/行） |
| **预算原口径：单事务 1000 条** | **10.07 / 10.54 / 11.62 ms** | ❌ **只作参照，不判定** | **`hbot_store` 没有这个 API**；参照值由本 crate 用 `rusqlite::Connection::unchecked_transaction()` + 同一条 `INSERT` 直接写临时库得到，**不是 store 的能力** |
| 参照：rusqlite 自动提交 1000 条 | 118.31 / 123.97 / 125.56 ms | ❌ 只作参照 | 用来证明「1000 个事务的代价 = 118–126 ms」，即逐条路径的时间基本全在 commit |

**结论**：按现行逐条 API 是 **141 ms < 200 ms，通过**，但这是**最轻那三次**的数字；后续四次运行测到
**175.86 ms（批次 B）/ 187.67（F）/ 189.24（D）/ 190.41（E）**——即**典型余量只有 5 %**，而且几乎全是 1000 次 commit 的 fsync。
它是单事务口径的 **13×**。如果将来入站突发要走「1000 条一批」，**需要 store 提供批量事务 API**（本 crate 不代为实现，只报缺口）。
这一项**属于负载一高就会翻车**的类型，建议按「擦线通过」对待。

## §4 QuickJS 吞吐（有条件通过：稳态 1.25×，负载 100 时 2.64×）

- 1000 事件 mean：**37.00 / 43.10 / 44.00 µs**（批次 A），对回归线 68.8 µs（= S1 的 34.4 µs × 2）通过，**1.25× S1**。

  五次的分布是 37.0–90.8 µs（2.5× 的跨度），**代码没有任何改动** —— 差异全部来自机器负载（同时有 5–19 个 cargo/rustc/link
  进程 + Defender 实时扫描）。所以这条线在共享构建机上会**假红**：判退化前必须先确认当时 `env_load_percent` / `env_concurrent_builds`。
  建议：要么把回归线放成 3×（103 µs）并只在**独占机**上跑 2× 判定，要么在 CI 上把这条线与「负载」一起记录、超线时重跑。

- **偏离 > 2× 的单次项**（如实标出）：`quickjs_compile_cold` 3.71–8.31 ms（S1 3.10 ms，1.2–2.7×）、

  这三项都是**单次冷路径**，且测量时机器上有 8–19 个并发编译进程 + Defender 在扫 DLL ⇒ 判为**机器/负载差异**，
  不判为退化（稳态 1000 事件均值只偏 1.25×，这才是可比的量）。
- 内存侧交叉验证：isolate 自报堆 101 KiB used / 113 KiB malloc（S1：100/112 KiB），**一致**。

## §5 内存：每 isolate 私有提交（通过）

- 口径：**`PrivateMemorySize64` 在进程树上求和**。isolate 是 `hbot-code` 里的**线程**（不是子进程），
  所以「进程树」= 本进程一个 PID；采样直接查自己 PID（5 次 × 200 ms 取中位），
  **不用** `scripts/mem-probe.ps1 -IncludeChildren` —— 那个脚本是从外部枚举**后代进程**求和，
  而本 crate 一旦 spawn 它，PowerShell 自己（约 70 MB）就成了被测进程的后代，会把 8 MB 的判定彻底污染。
- 实测：基线 2.33–3.57 MB →（+8 个 isolate）4.66–5.86 MB，增量 ÷ 8 = **0.23 / 0.26 / 0.29 MB/isolate**，
  对 8 MB 预算余量 **27×**；与 ADR-0002 §4 的 0.30 MB、S1 的 0.30 MB **一致**。
- 交叉验证：全部 drop 后 3.09–3.57 MB（相对基线 +0.76–0.97 MB）—— 分配器保留但未还系统，属正常。
- 口径边界：这条**不含**主进程以外的东西；「桌面整机 < 260 MB」「核心空闲 < 60 MB」「每多一个 bot < 6 MB」
  需要真实二进制与真实连接，本次**未测**（见下）。

**归因一句话（改前）**：4 条超预算其实是**同一个瓶颈**（10k 次「stat + 整文件读」），不是 4 个独立问题。
把每文件成本从 151 µs 压到 <100 µs（10k × 100 µs = 1 s）就能全部达标；压低的手段在 IO 层，不在正则层。

**改后归因一句话**：瓶颈确实在 IO 层，而且**改法奏效的次序**也印证了这一点 —— 先去掉 10k 次 stat（省 ≈450 ms，对上 §1 的 `walk_metadata` 453.90 ms），再并行读（轻负载再省 ≈400 ms，重负载几乎为零）。匹配算法**一行没动**。

| 冷启动到核心可用 / 到可交互 < 800 ms | 同上，需真实桌面/CLI 产物；ADR-0002 §4 记 878 ms / 924 ms（**当时就不达标**） |
| 按键延迟 p95 < 16 ms、UI 首屏 < 1 s、初始 JS(gzip) < 1.5 MB | 需要 renderer 运行时（WebView2），Rust 侧量不到；属桌面端 spike |

| **真冷盘**搜索/读（清 standby list 后） | 需要管理员权限清文件缓存或重启；本机非管理员、且是共享构建机不能重启。所以「冷」= **进程内第一次调用**（文件刚由夹具写出，仍在 OS 缓存里）—— 这是真冷盘的**乐观下限** |
| Defender 对每文件开销的贡献占比 | 关实时保护需要管理员。只能记录 `OnAccessProtectionEnabled=True` 并给出「每文件固定开销 151 µs」的结构证据，**未做 A/B** |

| `available_parallelism()` 在 CI 容器里的取值 | 本机是 20。容器里它常返回**配额核数（CPU quota）**而不是宿主机核数，也可能因 cgroup 只暴露 1 核而退化为串行。代码已夹在 `1..=64`，最坏情况退化为单线程（仍是改后 660.85 ms 那条路径），**但没有在容器里实测** |

## 对设计的影响

1. **搜索不是算法问题**，`docs/05-quality-gates.md` 的那条预算在 10k 小文件 + 实时防护下**天然吃紧**。
   要达标必须动 IO 结构（并行 / 首屏只读前缀 / 索引），而不是换正则引擎。这条结论已反过来影响实现方向：
   批次 A 时按任务约束**只写证据、没改 `hbot-workspace`**；**批次 G 起按这条结论动了实现**（`crates/hbot-workspace/src/search.rs`：
   去每文件 stat + 并行读匹配，匹配算法一行未动），4 条预算改后中位全部回到线内（G.1）。
2. **回归基线怎么定**：本指标在共享构建机上波动 1.0–2.6 s（改前）／141 ms–1157 ms（改后，**8× 跨度**），**不能直接当基线**。
   建议 nightly 在独占机器跑 `cargo run -p hbot-bench --release`，并把 `env_concurrent_builds` 一起入库；
   本 crate 已把机器/负载/Defender 快照、以及 `search_10k_threads`（并行线程数）打进每次输出。
   判退化时**先看负载列**：改后 3 次重负载运行各有一条超线，全部发生在 `env_concurrent_builds ≥ 4` 时。
3. **CI 接入**：`cargo test` 那条路径永远 exit 0（断言的是「量到了」），闸门只能由 `cargo run -p hbot-bench --release` 承担
   （有 FAIL 就 exit 1）。写 spike/看趋势时用 `--report` 让它 exit 0 —— **不要**把 `--report` 接进 CI，否则就是假绿。
4. store 的「1000 条」预算建议改成两个数：**逐条 API < 200 ms**（现状 141 ms）与
   **将来批量 API 目标 < 50 ms**（单事务参照 10.5 ms，留 4× 余量给事务外开销）；现在文档里只有一个「单事务 < 200 ms」，与实现不匹配。

## 未验证 / 已知不确定

- 三次运行都在**共享构建机**上（负载 91–100），搜索数字的可比性限于「负载相近」；真正的空闲基线未取到。
- **改后（批次 G）同样是共享构建机**：重负载 3 次（负载 99/77/88、并发编译 14/4/6）与轻负载复核 3 次（负载 97/77/82、并发编译 12/3/1）。
  两轮同一份代码，中位数差 2.1–3.9×（热 746.31 vs 251.63），所以本文件一律同时给两轮的 min/median/max，**不取平均、不挑最好那次当成绩**。
- **改后的「达标」是「中位达标」**：3 次重负载运行里每条判定行各有 1 次超 1000 ms。没有独占机器、没有清 OS 缓存，就无法给出「稳定达标」的结论。
- 另一轮（批次 B）数字与批次 A 差 1.4–1.7 倍，已按「不取平均、分别列出 + 说明并发污染」处理；**不能**把两者混成一条基线。
- 每 isolate 0.14 MB（批次 B）vs 0.23–0.29 MB（批次 A/C）：批次 B 的口径细节未知（isolate 数量/预热顺序可能不同），
  两者都远低于 8 MB，未进一步追平。
- `quickjs_isolate_spawn` 的 34.82 ms 是单次冷路径 + 负载尖峰，样本 n=1/次运行，**不足以**作为退化判据。

## 附：读日志的坑（本 crate 使用时会遇到）

- PowerShell 重定向 `*>` 读子进程输出时按 **GBK** 解码，而 `cargo`/本 crate 输出的是 UTF-8 中文说明：
  中文会糊成乱码，**并且中文字节后面的换行会被当成非法尾字节吃掉、多行粘成一行**。
  跑之前先 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`。数值（ASCII）不受影响，
  但日志不可读、按行解析会漏行（本次就踩到了，解析器最后改成在全文上正则匹配）。
- 长命令一律 `*> 日志文件` 再读文件：PowerShell 管道写满会假死。
