# ADR-0007 · 不在构建期引入 Node 工具链（`E1` 的结论）

- 状态：**Accepted**（2026-11-20）
- 相关：[ADR-0002](0002-agent-in-rust.md)（Agent 在 Rust，无 Node）、`docs/07-bot-runtime-blueprint.md` §6（`E1` 打包）、`AGENTS.md` §0 硬规则 1 与 9

---

## 1. 背景

`docs/07` 的能力表里 `E1`（npm 打包 / 依赖安装）一直记作「设计」。它来自一个真实需求：**写 bot 的人想用现成的库**。旧项目就是这么干的 —— 一个 `node_modules`、一个 `package.json`，`npm i` 之后 `import dayjs from 'dayjs'`。

本项目从第一天起就有一条相反的硬规则（`AGENTS.md` §0）：

> **产品运行时不允许 Node**：不 `spawn node`、不加 `node_modules` 运行时依赖、不把 Agent 放回 V8。
> **代码是唯一真源**：多文件项目、相对 import；没有隐藏的 flow.json / 数据库里的逻辑。禁止裸包名与 npm。

于是 `E1` 的真实问题不是「怎么实现打包」，而是：**为了用第三方库，要不要把 npm 引入构建期？**

## 2. 决策

**不做。`E1` 从能力表移除，理由不是「麻烦」，而是它会把两条硬规则一起推翻。**

### D1 裸包名会让「代码是唯一真源」失效

用户代码现在只允许两种 import：`hbot`（宿主白名单）与**相对路径**（同项目内的多文件）。这条约束换来一个性质：**拿到项目目录就能完整理解它的行为**。

一旦允许 `import _ from 'lodash'`，项目的行为就取决于：

- `node_modules` 里到底装的是哪个版本（这个目录通常不进 git）；
- 它自己又依赖了什么（传递依赖）；
- 那些依赖在运行时做了什么（读文件？发网络请求？）。

宿主沙箱对「项目里的 `.ts`」有一套判据（`permissions.http` 管网络、`capabilities` 管能力），**但对 `node_modules` 里的任意 JS 没有**：它是普通代码，却不在隔离边界内。这不是「放松一点」，是「隔离边界上开了一个洞，洞里是任意第三方代码」。

### D2 引 npm 就必须引 Node，而 Node 一旦进来就不会只停在构建期

要用 npm 装包、要 `require` 的解析语义（`main`/`exports`/条件导出/CJS-ESM 互操作），实际上就得用 Node 自己来解析与打包。于是构建期多一个 Node 工具链：

- 用户机器上要有 Node（今天只需一个 `hbot` 二进制，13.96 MiB 安装包）；
- CI 要多一条工具链版本矩阵；
- 打包产物要内联或旁挂 `node_modules`，安装包体积与「首次启动解压」成本都跟着涨；
- 最要命的是**解释权的迁移**：模块解析从「宿主的规则」变成「Node 的规则」，而 Node 的解析规则是 TLV 式的隐式查找（向上找 `node_modules`）。同一句 `import 'x'` 在两个项目里可以解析到两个不同文件，且**从源码看不出来**。

`hbot-code` 现在的编译路径是 SWC（Rust，进程内），模块图由宿主自己按相对路径构建。这条路径**没有 Node，也没有隐式查找**。把它换成 Node 打包，等于把整条编译链路交给一个我们无法约束的外部实现。

### D3 「不能用第三方库」不等于「什么都写不了」

真正被挡住的只有「把一个 npm 包塞进来」。用户的多数诉求已经有宿主侧答案：

| 想要的 | 现在的答案 |
|---|---|
| HTTP 请求 | `ctx.http`（`permissions.http` 管目标） |
| JSON / 字符串 / 日期处理 | 纯 TS 自己写；运行时是完整 QuickJS，标准库够用 |
| 持久化 | `ctx.kv` / `ctx.sql`（每 bot 一个库文件）/ `ctx.history` |
| 定时与后台 | `onSchedule` / `ctx.jobs` |
| 调模型 | `ctx.ai` |
| 读写项目文件 | `ctx.files` |
| 发消息 | `ctx.reply` / `ctx.send` / `ctx.notify` |

缺的那一类是「体积大、逻辑复杂、且必须与外部世界对表」的库（时区数据库、解析器生成器、加解密套件）。这类需求的正确形状是**宿主提供能力**（例如将来的 `ctx.crypto`），而不是「让每个项目各自 `npm i` 一份」：前者只有一份实现、可审计、可测；后者每个项目一份、版本各异、且都在隔离边界之外。

## 3. 备选方案与否决理由

| 方案 | 为什么不选 |
|---|---|
| A 允许 `node_modules`，运行时用 Node 跑 | 直接推翻 §0 硬规则 1，且失去了 isolate 的内存/时间/调用上限（Node 子进程的预算要另一套） |
| B 构建期用 Node 打包成单文件，运行时仍进 QuickJS | 解决了「运行时不带 Node」，但把隐式模块解析与第三方代码带进了产物；且构建期多一条工具链（D2）。仍然违反「代码是唯一真源」 |
| C 只允许**经过审阅的白名单**包，内联进宿主 | 看上去折中，实际是「宿主提供能力」的劣化版：白名单里每个包都要在隔离边界内被信任，而它们的实现不在我们的测试范围内 |
| D 宿主按需长能力（本 ADR 的选择） | 每一项都要单独设计、单独测、单独记文档，慢；但每一份实现只有一处，且天然在隔离边界内 |

## 4. 后果

- **正面**：项目目录 = 完整行为；沙箱边界没有「第三方代码」这个例外；安装包不需要 Node；`hbot check` 能对全部 import 做判据。
- **负面**：用户不能「顺手装个包」。遇到宿主没有的能力，只能提需求或自己写。这是刻意的取舍 —— 与 `ADR-0002`（Agent 在 Rust、不用 V8）是同一条线的延伸。
- **对文档的影响**：`docs/07` 的 `E1` 行改为「不做（ADR-0007）」，不再出现在「未开始」清单里；`README` 的未完成项去掉打包，只留平台移植与云端宿主。
- **可逆性**：如果真有一天要做，正确的入口是「宿主新增能力」而不是「放开 npm」；本 ADR 不排除将来引入**受控的** WASM 插件（`C3.wasm` 已在能力表里，`docs/07` §3），因为 WASM 有明确的导入表，能被宿主逐项约束 —— 那是与 npm 完全不同的问题。
