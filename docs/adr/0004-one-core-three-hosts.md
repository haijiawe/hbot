# ADR-0004 · 一个核心，三个宿主（含手机端）

- 状态：**Proposed**（2026-11-17）
- 取代：无。补充 [ADR-0002](0002-agent-in-rust.md)（Rust 单核 + Tauri 2 + QuickJS），不改变它的技术选型，只扩展**宿主范围**。
- 相关：`docs/07-bot-runtime-blueprint.md`（能力面）、`docs/08-multi-host.md`（宿主矩阵）

---

## 1. 背景

用户目标（2026-11-17）：

> 我不限制各种 bot 开发，差不多基本都是在这个项目上开发，未来还会搞手机端的，让手机端也能运行 bot，差不多基本就是 agent 写 bot 的代码。

三条约束同时成立：

1. **不限形态**：聊天 / 群游戏 / 客服 / 监控 / 自动化都要能写（→ 见 `docs/07`，能力分层）。
2. **同一份 bot 代码**：用户不想为桌面和手机各写一遍。
3. **Agent 写代码**：代码由模型生成，宿主必须能约束它。

手机端不是"再出一个客户端"，而是**第四个运行位置**：bot 真正跑在手机上（用手机的网、手机的常驻性、手机的账号登录态）。

---

## 2. 决策

### D1 一个核心，三个宿主，一份契约

```text
        hbot-core（领域 + 端口）
              │
   ┌──────────┼──────────┐
 桌面 Host   无头 Host   手机 Host
 Tauri 2      hbot serve  Tauri 2 mobile
（同进程）    （同进程）    （同进程，Rust 静态链接进 lib）
```

- **同一份 `hbot-core`** 链接进三个宿主，不通过 sidecar、不起子进程。
- **同一份 RPC 契约**（`crates/hbot-rpc/src/dto/`，24 命令 / 12 事件，ts-rs 生成 TS）。
- **同一份项目格式**（`hbot.json` + `bot.ts` + `.hbot/hbot.db`）。
- 宿主之间唯一的差别是**能力矩阵**（`docs/08` §3），不是代码分叉。

### D2 手机端是"宿主 + 精简控制台"，不是完整 IDE

手机上**不做** Monaco 多文件 IDE：

- 屏幕与键盘决定它写不了代码；Monaco 在移动 WebView 的按键与滚动体验不可用；
- 但**手机必须能启停 bot、看日志、注入一条测试消息、审批 Agent 的工具调用**。

完整 IDE 走**远程连接**：手机上的 daemon 监听 loopback（官方 localhost 插件支持移动端），桌面 IDE 通过局域网 RPC 连过去编辑同一份项目。这样"在手机上跑、在桌面写"成立，而不用做两套编辑器。

### D3 继续用 TypeScript + QuickJS，不用 V8/Node

- QuickJS 是**纯解释器，无 JIT**。iOS 只允许 WebKit 的 JIT，第三方 JS 引擎带 JIT 会被审核与运行时双重拦截；解释器路线在 iOS 上是唯一稳妥选择。
- 内存实测 0.30 MB/isolate（`docs/spikes/S1-quickjs.md`），手机比桌面更需要这个数字。
- 代价：执行慢（34–72 µs/事件，对我们够用）、生态缺 npm（补法见 `docs/08` §5）。

### D4 移动端不加 sidecar、不起子进程

Tauri 官方 shell 插件在 Android/iOS 上**只能 `open` URL，不能执行命令**（<https://v2.tauri.app/plugin/shell/>）；`bundle.externalBin` 只覆盖桌面 target。所以"手机端挂一个 Node sidecar"这条路不存在。

这一条反过来证明了 ADR-0002 当初"核心静态链接进 Tauri、不要 sidecar"的选择是对的：**它让手机端成为可能**。若当初选了 Electron + Node daemon，手机端就得从头再做一个运行时。

### D5 能力按宿主裁剪，而不是"手机功能少一点"

宿主启动时探测能力（能否执行命令、作业预算上限、有无设备能力），把结果写进**能力矩阵**；`hbot.d.ts` 与 Agent 工具表都由矩阵生成。手机上不出现 `run_command`，不是因为"我们懒得实现"，而是 d.ts 里根本没有这个函数（→ `docs/07` §7.2）。

## 3. 备选方案与被否理由

| 方案 | 内容 | 否决理由 |
|---|---|---|
| **A** 手机端独立实现（另一套运行时） | 手机用 Kotlin/Swift 重写 bot 运行时 | 两份语义必然漂移；Agent 生成的代码无法保证两端都跑得对；维护成本翻倍 |
| **B** 手机只做遥控器，bot 跑在家里桌面 | 手机连回桌面 | **不否决，作为降级路径保留**：如果 Tauri mobile 或 iOS 审核走不通，就退到这条 |
| **C** bot 跑在云上，手机只是客户端 | 云端多租户 | 与"本地优先、数据不出机器"冲突；要服务器成本与运维；手机断网就用不了 |
| **D** 手机端用 Node/V8 sidecar | 与桌面旧方案一致 | 移动端不能起子进程（D4）；V8 的 JIT 在 iOS 不可用（D3） |
| **E** 手机端做完整 Monaco IDE | 一套代码两端一致 | 移动输入体验不可用；包体与内存都要翻倍；而"写代码"本来就在桌面 |

## 4. 后果

### 4.1 必须承担的

1. **两套 WebView**：Android 是系统 Chromium WebView（版本随设备），iOS 是 WKWebView（版本随系统，不能独立升级）。前端必须同时兼容两套引擎；iOS 上老系统无法靠升级绕过。
2. **iOS 构建门槛**：只能在 macOS 上构建，需要 Apple Developer 计划（约 99 美元/年）与设备签名。
3. **Android 构建门槛**：Android Studio + SDK/NDK + Java keystore 签名。
4. **"手机 24 小时在线"不能承诺**：iOS 后台执行受限、Android 有 Doze 与前台服务类型约束（细节见 `docs/08` §4）。产品文案必须写明"前台/常驻通知下运行"。
5. **项目文件在手机沙盒内**：fs 访问被限制在应用目录，导入/导出要显式做（zip 或 git）。

### 4.2 可以接受的

- 手机端启动慢一点（WebView 初始化比桌面更贵）。
- 手机端只支持部分平台适配器（`onebot11` 能连局域网 NapCat；`qq_official` 走出站 WS，也能用）。
- 手机端 `jobs` 预算比桌面短一个数量级。

### 4.3 不能接受的（重估信号）

| 信号 | 处置 |
|---|---|
| Tauri mobile 在我们需要的功能上阻塞 > 2 周 | 退回方案 B（手机只做遥控器） |
| iOS 审核因"应用内执行生成的代码"被拒 ≥ 2 次 | iOS 只出 TestFlight/企业分发，或直接放弃 iOS 只做 Android |
| WKWebView 跑不动我们的控制台（帧率或兼容性） | 手机端控制台换成原生视图（Kotlin/Swift），daemon 不变 |
| Android 前台服务被商店判定滥用 | 改成"打开应用才运行"模式 |
| 手机端内存 > 300 MB | 重新评估是否把 IDE 的控制台做成原生 |

---

## 5. 可逆性

- RPC 契约是唯一的缝：只要 `Command`/`Event` 不变，宿主可以换（Tauri→别的壳、手机→遥控器）。
- 能力矩阵是数据，不是代码分支：去掉手机端不影响桌面端任何一行。
- 项目格式与 `hbot.db` 三端一致，迁移方向单一。

---

## 6. 实施顺序（不改变当前里程碑）

手机端**不插进 M0–M6**，作为 M7 之后的新里程碑（`docs/08` §7）：

1. 先把 `docs/07` §11 的能力底座（kv / history / ai / timer / jobs）在桌面做扎实；
2. 再做 Android（无审核门槛，验证"手机能跑 bot"这个假设）；
3. iOS 最后做（审核与构建成本最高）。

**理由**：手机端 90% 的工作量是"宿主移植"，10% 是"能力裁剪"。能力底座没做好就移植，等于把四种半成品复制到三个平台。
