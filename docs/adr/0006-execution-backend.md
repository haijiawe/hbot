# ADR-0006 · 运行位置可选：本机 / 局域网 / 云端

- 状态：**Proposed**（2026-11-17）
- 补充：[ADR-0004](0004-one-core-three-hosts.md)（三宿主：桌面/无头/手机）。宿主回答"跑在哪类设备"，本 ADR 回答"那台设备是谁的"。
- 相关：`docs/08-multi-host.md` §9（运行位置设计）、`docs/02-architecture.md` §9（RPC 契约）

---

## 1. 背景

用户 2026-11-17：

> 没有限制，当然也可以在设置修改，要么本地要么云端。都可以的。

诉求是**一个项目可以选择在哪跑**：自己电脑上、局域网里的另一台机器、或者一台云服务器。不是"两个产品"，是"同一个产品的部署选项"。

已有的技术事实决定了这件事的难度：

- 核心已经是**一个二进制**（`hbot.exe` 18.05 MiB / `hbot serve` 36.4 ms 到 ready），桌面壳只是它的第一个宿主。
- 桌面与无头**本来就是同一个组合根**（`Dispatcher::with_state`），走同一份 24 命令 / 12 事件契约。
- RPC 层已经有 token 校验、Origin 白名单、首帧认证 5 s 超时、1 MiB 帧上限、32 in-flight。

也就是说：**"云端"不是新架构，是把已有的 `hbot serve` 绑到公网并补上传输与运维。** 真正需要决策的是边界：谁能写、搬不搬家、承诺什么。

---

## 2. 决策

### D1 位置是一档部署选择，不是架构分叉

四档，共用同一核心与同一份契约：

| 档 | 核心在哪 | IDE 怎么连 |
|---|---|---|
| L0 | 桌面同进程 | Tauri IPC |
| L1 | 本机 `hbot serve` | `ws://127.0.0.1:<port>` |
| L2 | 局域网另一台机器 | `wss://<lan-host>:<port>` |
| L3 | 云服务器 | `wss://<domain>:<port>`（或反向代理终止 TLS） |

L2/L3 与 L0/L1 的差别**只在传输与部署**，运行时的消息链路、队列、沙箱、审计全部相同。这条性质必须保持——一旦"云端版"有独立代码路径，手机端的"一份契约"就不成立了（`ADR-0004` D1）。

### D2 单一写者：远程 IDE 是客户端，不是第二个写者

- 一个项目的 `hbot.db` 在任一时刻**只有一个核心**能写。
- 远程 IDE 发的仍是 `Command`，由那一个核心串行化落盘。
- **不支持**"桌面跑一份、云端跑一份、共享同一项目目录"。那需要分布式一致性，不是本产品要解决的问题，且会直接破坏"消息不丢"这条不变量。
- 第二个核心打开同一项目时**必须报冲突**（`H8` 的验收：两进程指同一目录，第二个失败），而不是"两个都能跑"。

### D3 换位置 = 搬家，不做热迁移

流程固定：`bot_stop` → 导出（git 或 `hbot export`）→ 目标机 `project_open` → `bot_start`。

理由：热迁移要保证"迁移瞬间在途消息不丢、不重放、不串号"，这需要分布式队列与两阶段切换；而实际使用中换位置的频率是"偶尔"，不是"每天"。用明确的中断换确定的行为。

### D4 非 loopback 绑定必须显式、且必须配 TLS

- 默认只绑 `127.0.0.1`。这是**安全默认**，不能被配置文件"顺手"改掉。
- 绑非回环地址时：显式 flag + 启动横幅警告 + 写入日志。
- **未配 TLS 且绑非回环 → 拒绝启动**（不是警告）。理由：`ws://` 明文会把 token 与全部消息内容暴露给链路上任何人，这不是"用户自己承担风险"能解释的——用户通常不知道自己在明文传输。

### D5 认证按客户端发 token，不共用一个

- 本机单 token 足够（进程边界就是信任边界）。
- 公网必须能独立吊销：每个客户端一枚 token，`hbot token issue` / `hbot token revoke`，登录审计，失败退避。
- 这一条同时解决了"手机端走局域网连桌面核心"的认证问题（`08` §8 的局域网直连）。

### D6 云端不提供设备能力，且明确"一台云主机 = 一个用户"

- `device` 在云端不可用（没有显示器与输入设备）。这是物理事实，不是限制（`ADR-0005` D6）。
- 当前的 `workspace-write` 命令沙箱是"限制在项目目录"，**不是"用户 A 看不到用户 B 的项目"**。真正多租户需要容器或独立系统用户，属另一个产品形态。
- 文档与 UI 都要写明这条边界；不靠"用户应该知道"来兜底。

### D7 云端密钥：没有 keychain 时显式降级，不静默

Linux 服务器通常没有 OS keychain。三条路：加密文件（口令来源待定）、环境变量、明文文件 + 告警。**必须在启动时明确说用了哪一条**（一条 `warn` 日志 + UI 状态），不能静默明文。具体选择留给 `08` §12 未决 9。

## 3. 备选方案与否决理由

| 方案 | 为什么不选 |
|---|---|
| A 只支持本机（不做远程） | 用户明确要云端；且远程 IDE 是手机端"局域网直连"的同一套能力 |
| B 云端做独立实现（独立服务 + 独立协议） | 立刻产生第二份契约；手机端与 IDE 都要适配两套。这正是旧项目"桌面/无头两套装配"的病根 |
| C 云端多租户（一台机器跑多个用户的项目） | 需要容器/独立系统用户/资源隔离与计费，是另一个产品；当前沙箱语义撑不住 |
| D 自动双向同步（本地与云端各一份，自动合并） | 需要冲突合并、多写者、离线队列——复杂度远超收益，且和 D2 直接冲突 |
| E 热迁移（不中断地把运行中的 bot 从本机搬到云端） | 见 D3，需要分布式队列；收益是"少停 10 秒"，代价是整条不变量链 |
| F 用 SSH 隧道代替 wss | 可行但把运维难度转给用户（要装 SSH 客户端、配密钥、管转发）；作为**文档里的推荐替代**保留，不作产品形态 |

## 4. 后果

**好的**：

- 一个项目可以在"我的电脑"和"一台 24h 在线的机器"之间选择，而不改变代码、不改变契约、不改变 IDE。
- 手机端的局域网直连（`08` §8）与云端的认证是同一套机制，一次投入两处受益。
- 拒绝启动这种硬失败（D4）比"警告后继续"更能阻止真实事故。

**代价**：

- 要补四件事：TLS 终止、多客户端 token、绑定确认、运维物（systemd/日志轮转/备份/健康检查）。都是"工程活"，没有架构风险，但也不是一两天。
- 编辑器每次保存/读取都要过一次公网：Monaco 输入是本地的，只有落盘往返，可接受；**1 MB 文件读取明显变慢**，远程时要在 UI 上避免"打开大文件"这类操作误以为是编辑器卡了。
- 云上"用户的平台凭据落在别人的服务器上"是**产品承诺问题**：文档必须说清"我们不托管你的账号，是你自己部署或明确选择的服务"。
- `H8`（未配 TLS 拒绝启动）会让一部分"我就想在内网快速试试"的用户被拦住——用 `--insecure-loopback` 之外的显式 `--allow-plaintext` 加二次确认来放宽，但默认拒绝。

## 5. 重估信号

| 信号 | 重新考虑什么 |
|---|---|
| 远程编辑的落盘往返 p95 > 300 ms（跨洲） | 引入"本地缓存 + 显式同步"模式，或建议用户就近部署 |
| 用户实际把云主机当多租户用（多人共用一个实例） | 要么做隔离（容器/独立用户），要么明确不支持并检查 |
| TLS 终止在反向代理后的场景占多数 | 简化内置 TLS，只做"相信代理"模式 + 强制 `wss` scheme 检查 |
| 云端出现"凭据被托管方看到"的争议 | 做端到端：凭据只在用户机器上加密，云端只拿到解密后的会话（需要重新设计） |
| 断线重连导致的数据不一致出现 ≥1 次 | 重新评估 D3（搬家）与 D2（单一写者）的执行严格度 |

---

## 6. 可逆性

- 远程是一个**传输层实现**：`WsConfig` 已有 `bind`/`token`/`allowed_origins`，加 TLS 与多 token 不影响 `Command`/`Event`。
- 退回"只支持本机"只需拒绝非 loopback 绑定——一条检查，不动契约、不动存储。
- 因此可以先做 `L1` 的加固（多 token + 绑定确认），再决定要不要花时间在 `L2/L3` 的运维物上。
