# ADR-0005 · 能力上限不砍，授权逐项给（含设备控制 C6）

- 状态：**Proposed**（2026-11-17）
- 补充：[ADR-0002](0002-agent-in-rust.md)（Rust 单核）与 [ADR-0004](0004-one-core-three-hosts.md)（三宿主），不改变技术选型，只确定**能力开放度的策略**。
- 相关：`docs/07-bot-runtime-blueprint.md` §3 与 §9（能力清单、C6 设计）

---

## 1. 背景

第一版蓝图对设备能力（C6）的处理是「单独立档、建议晚做」，理由是它与安全基线冲突。用户 2026-11-17 明确否掉这个收法：

> 都要，能力上限肯定越高越好，实现能力也能提升些不是吗，没有限制，当然也可以在设置修改，要么本地要么云端。都可以的。

拆开来有三条诉求：

1. **能力上限不要人为砍**：砍掉 C6 等于永久排除「玩游戏的 bot」这一整类。
2. **但要能在设置里改**：不是"全都开着"，而是"默认关、我能逐项打开"。
3. **本地或云端都行**（后者见 [ADR-0006](0006-execution-backend.md)）。

所以真正要定的不是"要不要 C6"，而是**能力的默认值与授权粒度**。

---

## 2. 决策

### D1 能力上限不设人为天花板，但默认全关

- 能力清单（`07` §3 的 C1–C6）**按平台真实上限定义**，不为"安全"删条目。
- **默认值一律是关**：没在 `hbot.json` 声明的能力，生成代码里根本没有这个符号（d.ts 不生成），调用返回 `denied`，且**不进审批**——不能用"弹个窗让用户点通过"来补未声明的能力。
- 「不设上限」指的是**产品能力面**，不是**默认授权**。两者混在一起会把"支持"读成"默认允许"。

### D2 授权分三层，缺一层就拒

| 层 | 谁决定 | 粒度 | 默认 |
|---|---|---|---|
| 清单声明 | Agent 写、用户可见 | 按能力名（如 `device.input`） | 无声明=无能力 |
| 宿主设置 | 用户手动 | 按子能力 + **应用白名单** | 全关；白名单空=全拒 |
| 运行时会话 | 用户在场确认 | 限时（默认 5 min，上限 30 min） | 每次运行重新确认 |

关键性质：**清单声明不等于被允许**（第 2、3 层仍可拒），**宿主设置也不等于永久授权**（第 3 层每次运行都要）。这样"我给这个 bot 开过设备权限"不会变成"它以后随时能控制我的鼠标"。

### D3 危险能力按子能力拆，不按"组"授权

`device: true` 太粗。拆成 `screen` / `ocr` / `input` / `window` / `clipboard` 五项，`input`（键鼠注入）**单独二次确认**。理由：截图看和替我点鼠标不是同一个风险等级，一个开关会逼用户为了截图而给出点击权。

同样规则适用于未来的其它危险能力：粒度按**能造成什么后果**分，不按"实现上是不是同一个模块"分。

### D4 设备授权与文件沙箱档正交，UI 必须说清

- `read-only` 只约束文件与命令，**不代表不能控制鼠标**。这是反直觉的，必须在 UI 文案里写明，否则"只读"会被误读成"安全"。
- 反向：开了 `device.input` 时，UI 显示比沙箱档更醒目的状态（"这个 bot 可以操作你的鼠标"），并且在托盘常驻一个可见标记。

### D5 防护必须由宿主实现，不能指望平台

约定七条（`07` §9.3 展开）：不向安全桌面注入、锁屏拒绝、前台窗口白名单、速率与预算上限、审计不含像素与 OCR 原文、**像素与 OCR 文本一律当不可信数据**（提示注入新入口）、一键全局撤销（快捷键 + 托盘 + 命令三条路，撤销是"全部失效"而非"暂停"）。

### D6 各宿主按真实能力裁剪，不做假支持

| 宿主 | 能做 | 做不到就不做 |
|---|---|---|
| Windows 桌面 | 五项全做 | 受 UIPI 约束（进不去提权窗口）、锁屏拒绝、服务进程无桌面（设计而非缺陷） |
| macOS 桌面 | 五项全做 | 屏幕录制与辅助功能都要用户手动授权；**录屏授权后需重启应用** |
| Linux X11 | 五项全做 | X11 本身没有授权机制 → **宿主自己的闸是唯一的闸** |
| Linux Wayland | 可以，但要走 portal | ScreenCast / RemoteDesktop 每次首次要用户在对话框确认；无 portal 的合成器不可用 |
| 无头 / 云端 | 全部不可用 | 没有会话与输入设备 |
| Android | `screen`/`input` 可用 | **只能侧载**：Play 政策禁止"自主规划并执行动作"，只允许固定规则脚本 |
| iOS | 全部不可用 | 无输入注入 API、读不到其它 App 界面树、录全屏需用户手动起 extension |

## 3. 备选方案与否决理由

| 方案 | 为什么不选 |
|---|---|
| A 不做 C6（第一版蓝图的做法） | 用户明确否掉：等于永久放弃"玩游戏的 bot"这一类 |
| B 做一个"完全放开"的档（一次授权永久全权） | 一次误点就永久交出键鼠，与"默认安全"基线冲突；且无法解释"我只想让它截图" |
| C 交给系统权限就够了（靠 OS 的辅助功能授权） | OS 授权是"这个 App 能不能控制电脑"，不是"这个 bot 现在能不能控制电脑"；粒度差一层 |
| D 用虚拟桌面/容器隔离跑设备 bot | 桌面虚拟化在 Windows/macOS 上要么需要管理员与 Hyper-V，要么无法访问用户的真实窗口；与"操作我正在玩的游戏"这个目标直接冲突 |
| E 只做 RPA 式（录制回放固定脚本，不让模型实时决策） | 用户要的是 Agent 实时决策；固定脚本退化成旧项目的可视化编排 |

---

## 4. 后果

**好的**：

- 四类 bot（聊天/游戏/客服/玩游戏）在能力面上**全部可达**，不再有"这一类做不了"的产品缺口。
- 默认全关 + 三层闸，使"支持"与"默认允许"分开，风险由用户显式承担而不是被默认值吞掉。
- 子能力拆分让用户能"只给截图不给点击"，实际使用中绝大多数自动化只需要前者。

**代价**：

- 实现量最大的一项：三平台各一套 API + 权限流程 + 审计 + UI 指示 + 撤销链路（`07` §9.5 已估为独立里程碑 `M10`）。
- 审计与限流会增加运行时复杂度；`device` 的调用路径不能复用现有的 `ToolGateway`（它面向工具调用，"点一下鼠标"不是工具调用），需要独立的设备会话层。
- **无法防住所有滥用**：用户自己开的权限，配合提示注入，仍可能让 bot 做出用户没预期的操作。缓解是"限时 + 白名单 + 可见指示 + 可撤销"，不是"不会发生"。
- **Android 设备能力只能侧载**（Play 政策禁止自主型自动化，见 `08` §4.6）：这意味着"手机上的设备 bot"不能通过应用商店分发，用户要自己装 APK 并面对"未知来源"警告。这是产品可达性的损失，不是技术损失。

## 5. 重估信号

| 信号 | 重新考虑什么 |
|---|---|
| 真机上"前台窗口白名单"误拦率 >30% | 白名单默认值改为"当前前台应用"，并要求用户每次会话确认 |
| 提示注入导致真实事故（哪怕是测试中） | 提高门槛：`input` 改为每次动作确认，或只在"专用会话"（全屏、无其它窗口）里允许 |
| Wayland 占比上升且用户要求 | 评估 xdg-desktop-portal 的 `RemoteDesktop` 接口（需用户每次共享），或明确只支持 X11 |
| 商店因无障碍/录屏拒审 | Android 侧改为"仅侧载"，不承诺上架（**已按此写进 `08` §4.6**：Play 政策明文禁自主型自动化） |
| 设备会话的撤销链路有可绕过的路径 | 全停 C6，回到 D4 之前的"档位互斥"设计 |

---

## 6. 可逆性

- 能力面在**契约层**是加法的：`Command` 里加设备相关命令、`Event` 里加设备状态，不改变既有 24 命令的语义。
- 关掉 C6 只需把 `capabilities.device` 从 d.ts 生成输入里移除（一个白名单），生成代码就不会引用它——**不需要改生成代码的产物格式**。
- 因此"先做底座、后做 C6"和"做了 C6 之后发现不行再关"这两种顺序都不需要重写。
